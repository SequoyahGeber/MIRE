# Full project audit — 2026-08-20

## Verdict

MIRE is not release-ready and its present performance claims are not sufficiently grounded in the
scene that actually ships. The audit found **22 new actionable findings: 6 high and 16 medium**
(`F-326` through `F-347`). The dominant risks are non-atomic player-data saves, duplicated
procedural streaming work on clients, quadratic enemy arbitration, destructive asset-verification
tools, renderer probes aimed at the retired authored level, and a navigation benchmark that now
reproduces 39-43 ms engine-frame stalls despite the owning decision remaining GREEN.

The project is nevertheless structurally coherent enough for continued development: every
code-bearing file parsed or passed its language-level validation, all runtime `res://` literals
resolved, the tracked scenes/resources are structurally loadable, no credential patterns were
found, and 174 of 188 stable Godot checks exited zero. It is safe to continue unrelated work with
the findings ledger as the queue. It is **not** safe to call saves crash-safe, navigation/renderer
performance proven, or the full regression suite green.

This was an audit only. No game source, scene, resource, project setting, or asset was changed.

## Medium-severity findings

- **Networking/authority:** ranged observers see a shot before recovery/hitstop is installed
  (F-327); `WorldDeltaLog` trusts an unbounded decompressed-size header (F-332); the shared 100 ms
  command throttle drops legitimate ordered RPC commands across three integration checks (F-333).
- **Lifecycle and verification:** the run-scope audit omits `MenuStack`, `PauseMenu`, and `RunRecord`
  (F-328); the complete loop passes its gameplay phases and then aborts during recursive-mutex
  teardown (F-334); title persistence expectations are stale and the POI negative control has lost
  its teeth (F-335); the harvest fixture is changed by live Mire state (F-343).
- **Performance:** Wellspring re-corruption rebuilds a full ward census per active Wellspring per
  frame (F-337); the saturated 65,536-cell Mire update has no worst-case time budget (F-338);
  remote interpolation misses its CV budget in both synthetic and live phases (F-344).
- **World generation/rendering/navigation:** jittered vertices keep normals from the unjittered
  grid (F-339); the 4.18 retune left structural assertions and 20 golden hashes stale (F-340);
  sway materials can share the wrong vertical pivot (F-341); co-op spawn offsets miss their own
  surface by up to 0.37 m (F-345); streamed navigation regions report overlapping raster edges
  (F-346).
- **Design documentation:** `GAMELOOP.md` still presents Hollowmere, two enemies, the old Attunement
  task number, and a missing run summary as current state (F-336).

## Stable automated battery

The stable Godot sweep ran **188 check scripts in 958.6 seconds**:

- **174 exited zero.** This includes final green results for biome terrain, chunk streaming, combat
  self-hit, day/night networking, navigation behavior, ranged networking, setup, registries,
  deterministic gameplay systems, menu surfaces, authority paths, content wiring, and most end-to-end
  lifecycle checks.
- **14 exited nonzero.** Two are environmental Steam checks because the Steam client was absent.
  The remaining 12 represent nine actionable classes: command throttling (three checks),
  seed-contaminated harvest expectations, interpolation smoothness, loop teardown, a broken POI
  negative control, incomplete run-scope classification, inaccurate co-op spawn heights, stale
  terrain/look goldens (two checks), and stale title persistence expectations.
- `loop_audit_check.gd` is special: all gameplay phases pass, then the process exits 250 during
  engine teardown. It is evidence of a shutdown defect, not a failed game-loop assertion.
- Many successful checks deliberately emit Godot `ERROR` lines while exercising negative controls.
  Exit status, declared failure summaries, and surrounding assertions were used instead of raw error
  counts, preventing expected rejection paths from being mislabeled as product bugs.

All 30 GDScripts withheld from execution because they render, overwrite assets, generate content,
or mutate setup state passed Godot `--check-only` with zero parser errors. All 50 Python scripts
parsed; all 5 shell scripts passed syntax validation. The harness and concurrent state-lock tests,
including HEAD baselines, passed.

## Measured performance

### Procedural terrain

`bench_chunks.gd` produced:

- ArrayMesh direct: **16.638 ms/chunk** single-threaded.
- SurfaceTool: **8.812 ms/chunk** single-threaded.
- WorkerThreadPool: **17.101 ms/chunk amortized** across 100 chunks.
- Only about one chunk fits in a 16.667 ms frame by the current benchmark.

The project's latest documented post-biome figure is 8.077 ms/chunk. The current result is roughly
2.06x that number and the worker path showed no throughput benefit. This reinforces open F-294's
per-sample allocation problem; it is not filed as a duplicate.

`bench_chunk_gpu.gd` found **1.330 ms** mean collision cook and **1.340 ms** steady main-thread cost
per streamed chunk, allowing about **2.98 chunks in a 4 ms slice**. GPU upload and material binding
were negligible in this isolated fixture. The 60-chunk issue phase still averaged 20.064 ms/chunk,
so this result must not be confused with a whole-world traversal budget.

### Navigation

Two `bench_navbake.gd` runs reproduced **39.457 ms** and **42.536 ms** worst engine frames during
the 24-chunk attach/retire episode. Single async submissions stayed cheap (0-0.092 ms), and seams
connected with a 1.10 m margin. The repeatable streaming spike invalidates the old 0.034 ms GREEN
evidence until profiled and corrected (F-347). Runtime checks additionally emitted overlapping-edge
synchronization warnings (F-346).

### Replication

The six-peer/200-entity spike remained CPU-cheap (worst host poll **1.311 ms/frame**), but its
bandwidth verdict is still AMBER. With interest filtering at 30 Hz it used **109.8 KB/s on the wire**;
at 15 Hz it used **59.9 KB/s**. The check itself states it models position/rotation dummy traffic,
not full current entity state, world streaming, latency, NAT, Wi-Fi, or upstream player movement.
It is useful capacity evidence, not a complete multiplayer load test.

### Renderer and late-run simulation

The available full renderer result (4,864 draw calls, 1,171,296 primitives, 278.2 MB VRAM, 9.35 ms
median on Apple M5 Pro) is for Hollowmere, not the procedural main scene, and therefore cannot
support a current shipped-world FPS claim (F-342). The 256 by 256 Mire simulation and its ward-heavy
late-run state also lack a worst-case budget gate (F-338).

## Design, system, and consistency conclusions

- Host authority is consistently designed and widely checked for inventory, crafting, building,
  combat, enemies, world deltas, Mire, cycle state, extraction, unlocks, and defeat. The most
  consequential audit discovery in this area is duplicated client-side streaming workload rather
  than an obvious host-authority bypass.
- The actual main scene is procedural. Menu systems are registered and tested, but the frontend is
  not yet the boot entry point. Some design documents describe the old authored-world/current-loop
  state as if it were live (F-336).
- The content registry is broad and internally loadable. The live count includes concurrent
  untracked ranged work, so clean-clone CI must not rely on the audit's four-ranged-weapon count.
- Direct file/path inspection found no missing runtime literal resources and no obvious embedded
  secrets. `git diff --check`, tracked-file presence, and repository object validation were clean at
  the audit snapshot.
- Seven production GDScripts exceed 800 lines; the 1,408-line `PlayerHealth` autoload spans several
  lifecycle domains. This is maintainability and review-cost debt, but no split is recommended
  without a task that preserves authority and signal contracts.

## Concurrency and snapshot integrity

Other agents were allowed to continue working. The first broad check run was discarded after the
terrain commit changed underneath it; the final 188-check sweep began only after the board was idle
and HEAD/origin had settled. Results were appended item-by-item to resumable JSONL ledgers. At
close-out, all 443 reviewed code hashes still matched. No concurrent source/resource/menu/ranged
changes were staged, committed, reverted, or incorporated. The only generated asset mutation caused
by this audit was the Blender reproduction check's tracked source/preview rewrite, and those exact
three paths were restored to HEAD immediately; that behavior is now F-329.

## Recommended repair order

1. F-326 atomic persistence and F-329 destructive verification, because both can destroy trusted
   data or other agents' work.
2. F-347/F-346 navigation streaming and F-342 procedural renderer instrumentation, because current
   playability/performance claims are otherwise not measurable.
3. F-330 client streaming multiplicity and F-331 enemy quadratic arbitration before larger
   multiplayer/wave tests make them expensive to unwind.
4. F-333 command ordering, F-332 decompression bounds, and F-327 ranged event ordering.
5. Refresh the broken/stale checks (F-328, F-334, F-335, F-340, F-343-F-345), then establish
   saturated Mire, ward, traversal, and six-peer procedural performance budgets.
