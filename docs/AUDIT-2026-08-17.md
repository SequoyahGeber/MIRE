# MIRE — project audit, 2026-08-17

Audit by `flint5`. Scope: the plan and its bookkeeping — `ROADMAP.md`, `NEXT.md`, `DECISIONS.md`,
`FINDINGS.md`, `DELEGATION.md`, `ASSET_TRACKER.md`, `AGENTS.md`, `CLAUDE.md`, `AI-WORKFLOW.md`, the
`.agent` board/state, and the `tools/` harnesses that back the claims those docs make.

**Everything under §1 was verified by running it** on `4.7.1.stable.official.a13da4feb`, with the
editor closed. Everything else is a documented cross-reference with `file:line` on both sides.

Headline: **the code is in better shape than the paperwork.** Every network seam, signal and
signature `DELEGATION.md` promises exists exactly as written — that contract is safe to build on. What
has drifted is the bookkeeping around it, and in four places the drift is now load-bearing.

## 1 · Broken right now — verified by running

### 1.1 `harvest_world_check` fails. It is the only red single-process harness. 🔴

```
ERROR: FAIL: actual map harvest grants three logs to offline inventory
HARVEST_WORLD_CHECK live=11 hidden=11 events=1 failures=1
```

`tools/harvest_world_check.gd:85` asserts `local_count("log") == 3`. `DevLoadout` grants **20 logs**
at spawn (`core/dev/dev_loadout.gd:34`), so the real count is 23. The harvest itself is fine — the
three preceding assertions all pass, the yield event fires with the right item and amount.

This is the exact breakage `core/dev/dev_loadout.gd:123` already documents: *"Four of them started
failing the moment this autoload existed."* Four were fixed; **this fifth one was missed and left
red.** Fix is to assert a delta, not an absolute.

### 1.2 `verify_setup.gd` prints "all checks passed" over 5 engine errors 🔴

```
SCRIPT ERROR: Invalid call. Nonexistent function 'new' in base 'GDScript'.
   at: PlayerController._build_viewmodel (res://entities/player/player_controller.gd:117)
...
all checks passed
```

`entities/player/viewmodel.gd` names `InventoryService`, `CombatService` and `Registry` as **bare
identifiers** — lines 51, 52, 56, 57, 69, 73, 102, 124, 125, 130, 136, 141. That is standing rule #1
in `DELEGATION.md:229` (F-011): a `--script` main loop compiles its dependencies *before* autoloads
are registered. `verify_setup.gd:158` reaches `PlayerController` by `class_name`, which preloads
`viewmodel.gd` (`player_controller.gd:36`), which fails to compile — so `.new()` at
`player_controller.gd:117` gets a broken `GDScript`.

The file knows the right pattern; it uses it correctly one line later at `viewmodel.gd:175`
(`get_node_or_null(^"/root/InventoryUI")`).

**The game itself is fine** — pressing Play works, because autoloads exist by the time a scene
loads. The blast radius is precisely the harnesses that reach `PlayerController` **at compile time**
(`verify_setup`, `interp_check`, `combat_feel_check`) — those run a player whose viewmodel script
failed to compile — while harnesses that `load()` the scene at runtime (`viewmodel_check`,
`dev_loadout_check`) compile it after autoload registration and are unaffected. The project's "run
it after anything structural" gate is in the first group, and reports success anyway.

F-041's close-out note cited this trap for 2.8's `player_controller.gd` and then reintroduced it one
file over, the next day.

### 1.3 The harness that was supposed to catch 1.2 cannot see it 🟠

`viewmodel_check.gd` reports `failures=0` and passes *"the owning player built a viewmodel under its
camera"* — because it loads the scene at runtime (`tools/viewmodel_check.gd:24`, `load()`) instead of
touching `PlayerController` by `class_name`. By then autoloads exist. Both harnesses are internally
correct; only `verify_setup` takes the path that breaks.

It also emits 8 engine errors of its own:

```
ERROR: Parameter "t" is null.  at: texture_2d_get
SCRIPT ERROR: Cannot call method 'save_png' on a null value.  at: _shoot (tools/viewmodel_check.gd:112)
```

`root.get_texture()` returns null under the dummy renderer, so **the "render per swing phase" evidence
in F-041's close-out does not exist in a plain headless run** — the calls are inert and the check still
returns `failures=0`.

### 1.4 The rule that would have caught all of this is not enforced

`DELEGATION.md:242`, standing rule #4: *"Grep every check run for engine errors — `2>&1 | grep -c
'ERROR:'` — and treat a non-zero count as a failure (F-021)."*

Measured across the single-process harnesses:

| Harness | exit | `ERROR:` lines | reported |
|---|---:|---:|---|
| `harvest_world_check` | 1 | 1 | `failures=1` 🔴 |
| `verify_setup` | 0 | **5** | `all checks passed` 🔴 |
| `viewmodel_check` | 0 | **8** | `failures=0` 🔴 |
| `combat_feel_check` | 0 | **4** | `failures=0` 🟠 |
| `interp_check` | 0 | **4** | (no failures line) 🟠 |
| `combat_check`, `crafting_check`, `crafting_ui_check`, `harvestable_check`, `inventory_check`, `inventory_ui_check`, `enemy_check`, `enemy_crawler_check`, `dev_loadout_check`, `interest_check`, `synced_group_check`, `handshake_check`, `run_identity_check`, `item_icons_check`, `playtest_hollow_check`, `playtest_map_check`, `environment_vfx_check` | 0 | 0 | clean ✅ |
| `enemy_facing_check` | — | — | not swept: a render diagnostic that ran 15+ min; run standalone |

The rule is written down, nothing runs it, and four harnesses were green over errors — all four
from the single §1.2 compile chain. That is precisely the F-021 failure mode it was written to
prevent — *"'two expected errors' is exactly the kind of allowance that later hides a third."*

### 1.5 `verify_setup.gd` checks 2 of 19 autoloads

`tools/verify_setup.gd:143-146` validates a hardcoded list of two — `DebugOverlay`, `DebugConsole`.
The other 17, including every gameplay service, have **no registration check anywhere**. A dropped
autoload line fails at runtime, not in the harness — which is the failure mode tasks 1.0 and 1.0b
exist because of.

## 2 · Loaded guns pointed at task 2.9 🔴

2.9 is inspector tuning of `.tres` files. Three generators overwrite exactly those files, and the two
most dangerous carry no warning. **Fix these before 2.9 starts, not after.**

| Generator | Overwrites | Warns? |
|---|---|---|
| `setup_combat_content.gd` | `content/weapons/stone_axe.tres` | ✅ `:7-8` |
| `setup_tool_content.gd` | 9 items + 7 weapons | ✅ `:14-16` |
| `setup_enemy_content.gd` | `content/enemies/crawler.tres` | ✅ `:6-7` |
| **`setup_crafting_content.gd`** | `content/items/stone_axe.tres`, `content/recipes/stone_axe.tres` | ❌ **none** |
| **`setup_harvest_content.gd`** | `content/items/{log,stone,iron_ore}.tres`, all 3 harvestable defs | ❌ **none** |
| **`setup_project.gd`** | `player.tscn`, `greybox_test.tscn`, **`project.godot`** | ⚠️ **contradicts itself** |

Three specifics:

- **`setup_harvest_content.gd` is destructive today.** `_save_item()` (`:64-72`) sets six fields and
  **never sets `icon`**. Running it silently strips the icons from `log`, `stone` and `iron_ore`
  (currently wired at `content/items/log.tres:5,12` and siblings) and the hotbar falls back to
  two-letter names. This is the identical loss that `setup_crafting_content.gd:26-27` records having
  already suffered once for `stone_axe` — the fix was patched into one file and never propagated.
- **`setup_crafting_content.gd`** hardcodes `grip_offset` / `grip_rotation_degrees` / `grip_scale`
  (`:38-40`) while its own comment at `:33-34` calls them *"starting points for the inspector."* It
  invites the tuning it destroys. Note the two halves of one weapon have different owners: the item is
  written here, the WeaponDef by `setup_combat_content.gd`, and only one warns.
- **`setup_project.gd:10`** says *"Re-running it is safe"* — then `:12-13` says the opposite. And
  `:31` sets `main_scene` to `greybox_test.tscn`, silently reverting the project from
  `playtest_hollow` (`project.godot:14`). `verify_setup.gd:10-12` deliberately does not pin the main
  scene (F-028), so nothing would catch the swap.

Current drift state: **no hand-tuning has happened yet** — every on-disk grip and weapon value still
matches its generator's formula. So the window to fix the warnings is open and costs nothing. It
closes the moment 2.9 begins.

## 9 · Decisions the project has made but never recorded

  rig and a Cycles icon renderer — and no CC0 pack was ever imported, though `ROADMAP.md:103` is marked
  done for exactly that. This reverses D-005 and the rationale at `DESIGN.md:251` (*"chosen because
  it's what CC0 asset packs give you for free"*), which `ASSET_TRACKER.md:48` still orders asset agents

  Blender version and Cycles seed, the same way D-001 pins Godot. Nothing pins Blender.
- **Content data may be bulk-generated by tool script** — a live exception to D-006 with a standing trap.
- **Asset production is agent work on a self-advancing queue** (2.1d promotes its own successor and
  hands itself back) — contradicts `AI-WORKFLOW.md:36` and the one-tier-per-task model.
- **`WeaponDef` / `HarvestableDef` / `BiomeDef` authorship rules** — D-006 predates all three.
- **A dev-only starting loadout and ambient spawning ship gameplay 2.12 specifies differently**, with
  no recorded removal condition before playtest.
- **M2 was rescoped 35 → 80 sessions.**

Also unscheduled: `DESIGN.md:246` specifies stamina gating a **dodge** that no roadmap task builds;
